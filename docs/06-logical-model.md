# 6. Логическая модель базы данных

Документ описывает логическую модель БД проекта **university-hr**: сущности, атрибуты, связи
и проверку нормальных форм. Диаграмма — `06-er-diagram.puml` (нотация «вороньи лапки», IE).
Физическая реализация (типы MySQL, индексы, кодировка) — день 7, файл `database/schema.sql`.

## 6.1. От объектов предметной области к сущностям

На день 1 мы выделили объекты данных. Теперь каждому объекту соответствует сущность (таблица),
каждому свойству — атрибут (столбец). Имена таблиц — английские, во множественном числе, в `snake_case`.
Эти имена фиксированы и используются во всех лекциях и лабораторных.

| Объект предметной области | Сущность (таблица) | Первичный ключ |
|---|---|---|
| Факультет | `faculties` | `id` |
| Кафедра | `departments` | `id` |
| Должность | `positions` | `id` |
| Сотрудник | `employees` | `id` |
| Пользователь (учётная запись) | `users` | `id` |
| Приказ | `orders` | `id` |
| Заявка на отпуск | `leave_requests` | `id` |

Везде используется **суррогатный ключ** `id` (автоинкремент). Естественные ключи (название факультета,
логин, номер приказа) тоже уникальны, но могут меняться, поэтому в связях не участвуют —
для них задано ограничение `UNIQUE`.

## 6.2. Атрибуты

|---|---|---|

## 6.3. Связи

| Связь | Тип | Кардинальность | Внешний ключ | Пояснение |
|---|---|---|---|---|
| Факультет — кафедра | 1 : N | 1 — 0..* | `departments.faculty_id` | На факультете несколько кафедр |
| Кафедра — сотрудник | 1 : N | 1 — 0..* | `employees.department_id` | Сотрудник числится ровно на одной кафедре |
| Должность — сотрудник | 1 : N | 1 — 0..* | `employees.position_id` | |
| Сотрудник — кафедра (заведует) | 1 : 1 | 0..1 — 0..1 | `departments.head_employee_id` | Необязательная связь, кольцо со связью «числится» |
| Сотрудник — пользователь | 1 : 1 | 0..1 — 0..1 | `users.employee_id` UNIQUE | Связь 1:1 реализуется через FK + UNIQUE |
| Сотрудник — приказ | 1 : N | 1 — 0..* | `orders.employee_id` | |
| Пользователь — приказ | 1 : N | 1 — 0..* | `orders.created_by` | Кто оформил |
| Сотрудник — заявка | 1 : N | 1 — 0..* | `leave_requests.employee_id` | |
| Пользователь — заявка (решения) | 1 : N | 0..1 — 0..* | `head_decision_by`, `hr_decision_by` | Две связи с одной таблицей |

Связь «многие ко многим» в MVP не нужна. Если разрешить совместительство (сотрудник на нескольких
кафедрах), появится связующая таблица `employee_departments (employee_id, department_id, rate)`.

**Циклическая ссылка** `departments.head_employee_id → employees` и `employees.department_id → departments`
допустима, но требует порядка вставки: сначала кафедры без заведующего, затем сотрудники, затем
`UPDATE departments SET head_employee_id = ...` (так сделано в `seed.sql`).

## 6.4. Нормализация

### Исходная «плоская» таблица
Так выглядели данные в Excel-файле отдела кадров:

| ФИО | Факультет | Кафедра | Зав. кафедрой | Должность | Категория | Отпуск с | Отпуск по | Статус отпуска |
|---|---|---|---|---|---|---|---|---|
| Рахимов Фарход Джамшедович | ФИТК | ПИС | Сафаров Д. Х. | Доцент | ППС | 01.07.2026, 01.12.2026 | 28.07.2026, 10.12.2026 | утв., ожидает |

Проблемы: несколько значений в одной ячейке, повторение названий факультета и кафедры в каждой строке,
аномалии вставки (нельзя добавить кафедру без сотрудника), обновления (переименование кафедры —
правка сотен строк) и удаления (удалили последнего сотрудника — потеряли кафедру).

### 1НФ — атомарность
Каждая ячейка содержит одно значение. ФИО делим на `last_name`, `first_name`, `middle_name`.
Несколько отпусков одного сотрудника выносим в отдельные строки → отдельная таблица `leave_requests`.

### 2НФ — нет частичных зависимостей от составного ключа
В таблице заявок ключом могла бы быть пара (сотрудник, дата начала), а атрибуты сотрудника
(ФИО, кафедра) зависят только от части ключа. Выносим сотрудника в `employees`; в заявке остаётся
ссылка `employee_id`. Во всех таблицах вводим суррогатный ключ `id` — составных ключей нет,
поэтому 2НФ выполняется автоматически, если выполнена 1НФ.

### 3НФ — нет транзитивных зависимостей
В `employees` было: `id → кафедра → факультет` и `id → должность → категория`.
Факультет зависит от кафедры, а не от сотрудника — выносим в `departments (faculty_id)` и `faculties`.
Категория зависит от должности — выносим в `positions (category)`.
Заведующий зависит от кафедры — храним в `departments.head_employee_id`.

Итог: все неключевые атрибуты каждой таблицы зависят **от ключа, от всего ключа и ни от чего, кроме ключа**.
Модель находится в 3НФ.

### Осознанная денормализация
`employees.status = on_leave` частично дублирует информацию из `leave_requests` (утверждённая заявка
на текущую дату). Мы храним статус явно, потому что он меняется не только из-за отпуска
(например, длительный больничный оформляется приказом), и по нему удобно фильтровать список.
Отчёт «в отпуске» считается по полю `status`.

## 6.5. Правила целостности

- **Ссылочная целостность**: все связи — внешние ключи InnoDB.
  - удаление сотрудника удаляет его заявки (`ON DELETE CASCADE`);
  - удаление сотрудника с приказами запрещено (`ON DELETE RESTRICT`) — уволенный сотрудник получает статус
    `dismissed`, а не удаляется;
  - при удалении сотрудника его учётная запись отвязывается (`ON DELETE SET NULL`),
    а кафедра остаётся без заведующего (`SET NULL`).
- **Доменная целостность**: ENUM для статусов и категорий, `CHECK (end_date >= start_date)`.
- **Уникальность**: названия факультетов и должностей, e-mail сотрудника, логин, номер приказа.
