## 4. Требования к системе

### 4.1. Требования к системе в целом

#### 4.1.1. Требования к структуре и функционированию
Система строится по трёхуровневой архитектуре «клиент — сервер приложений — сервер БД»
и по шаблону MVC (Model — View — Controller):

| Подсистема | Состав | Назначение |
|---|---|---|
| Представление | `views/*.php`, `public/assets/` | HTML-шаблоны, стили, клиентский JS |
| Маршрутизация | `public/index.php`, `App\Core\Router` | Единая точка входа, разбор URL |
| Безопасность | `App\Core\Session`, `Auth`, `Csrf` | Сессии, вход, роли, защита форм |
| Бизнес-логика | `App\Controllers\*`, `App\Services\LeaveRequestRules` | Обработка запросов, правила процесса отпуска |
| Доступ к данным | `App\Core\Database`, `App\Repositories\*` | PDO и SQL-запросы |
| Хранение данных | MySQL / MariaDB, база `university_hr` | Таблицы по `database/schema.sql` |

Обмен между браузером и сервером — HTTP/1.1 и HTTP/2 поверх TLS; формы отправляются методом POST,
просмотр — GET. Живой поиск обращается к JSON-ресурсу `/api/employees?q=`.

#### 4.1.2. Требования к численности и квалификации персонала
- Администратор системы — 1 человек, знание Linux, Nginx, MySQL на уровне администрирования.
- Пользователи (ОК, заведующие, сотрудники) — навыки работы с браузером; обучение не более 1 часа.

#### 4.1.3. Показатели назначения
- Объём данных: до 2000 сотрудников, до 10 000 заявок на отпуск.
- Время отклика любой страницы — не более 1 с при объёме данных выше.
- Время ответа JSON-поиска — не более 300 мс.
- Список сотрудников выводится постранично, по 10 записей.

#### 4.1.4. Требования к надёжности
- Ежедневное резервное копирование БД (`mysqldump`), хранение копий не менее 14 дней.
- Восстановление из резервной копии — не более 30 минут.
- При ошибке приложения пользователь видит понятное сообщение, подробности пишутся в журнал сервера
  (в рабочем режиме `display_errors = Off`).
- Изменения, затрагивающие несколько таблиц (утверждение отпуска + приказ), выполняются в транзакции.

#### 4.1.5. Требования к безопасности
- Доступ к страницам — только после входа (кроме `/login`).
- Пароли хранятся в виде хеша, полученного функцией `password_hash()` (алгоритм bcrypt).
- После успешного входа идентификатор сессии обновляется (`session_regenerate_id`).
- Cookie сессии: `HttpOnly`, `SameSite=Lax`, `Secure` при работе по HTTPS.
- Все SQL-запросы выполняются через подготовленные выражения PDO (prepared statements).
- Весь пользовательский вывод экранируется `htmlspecialchars()` (защита от XSS).
- Каждая POST-форма содержит CSRF-токен; запрос без верного токена отклоняется (код 419).
- Загружаемые файлы: проверка реального MIME-типа (`finfo`), размера, сохранение под случайным именем.

#### 4.1.6. Требования к эргономике и технической эстетике
- Адаптивная вёрстка на Bootstrap 5.3: от 360 px (смартфон) до 1920 px.
- Единый UI-kit (цвета, шрифты, компоненты) — `docs/09-design/ui-kit.md`.
- Сообщения об ошибках — рядом с полем формы, на русском языке.
- Статусы заявок выделены цветными бейджами и подписаны текстом (не только цветом).
- Контраст текста не ниже 4.5 : 1 (WCAG 2.1, уровень AA).

#### 4.1.7. Требования к эксплуатации и техническому обслуживанию
- Обновление версии — командой `git pull` на сервере (см. `docs/16-deploy.md`).
- Настройки подключения к БД хранятся вне репозитория (`config/config.php` или переменные окружения).

#### 4.1.8. Требования к защите информации от несанкционированного доступа
Права по ролям:

| Ресурс / действие | admin | hr | head | employee |
|---|---|---|---|---|
| Dashboard `/` | да | да | да | да |
| Список сотрудников `/employees` | все | все | своя кафедра | нет |
| Карточка `/employees/{id}` | все | все | своя кафедра | только своя |
| Создание, изменение, удаление сотрудника | да | да | нет | нет |
| Справочник `/departments` | да | да | да | нет |
| Список заявок `/leaves` | все | все | своя кафедра | только свои |
| Подача заявки `/leaves/create` | за любого сотрудника | за любого сотрудника | своя | своя |
| Согласование (pending → head_approved) | да | нет | своя кафедра, кроме своей заявки | нет |
| Утверждение (head_approved → approved) | да | да | нет | нет |
| Отклонение | на любом этапе | на этапе head_approved | на этапе pending | нет |
| Отчёт `/reports/staff` | да | да | да | нет |
| API `/api/employees` | все | все | своя кафедра | нет |

При попытке доступа без прав Система возвращает код 403 и страницу «Доступ запрещён».

#### 4.1.9. Требования к сохранности информации при авариях
Ежедневная резервная копия; хранение копий на отдельном диске или в облачном хранилище.
Фото сотрудников (`public/uploads/`) копируются вместе с БД.

#### 4.1.10. Требования к патентной чистоте
Используется только свободное ПО: PHP (PHP License), MySQL Community (GPL) / MariaDB (GPL),
Nginx (BSD), Bootstrap (MIT), PHPUnit (BSD-3).

#### 4.1.11. Требования по стандартизации и унификации
Код PHP — по рекомендациям PSR-1, PSR-4 (автозагрузка), PSR-12 (стиль). Документы UML — PlantUML.
Даты в БД — формат ISO 8601 (`YYYY-MM-DD`), в интерфейсе — `ДД.ММ.ГГГГ`.

#### 4.2.2. Функция «Сотрудники»
Поля формы и правила проверки:

| Поле | Обязательное | Правило |
|---|---|---|
| Фамилия, имя | да | не длиннее 60 символов |
| Отчество | нет | не длиннее 60 символов |
| Дата рождения | да | корректная дата, возраст от 18 лет |
| Пол | да | `m` или `f` |
| Телефон | нет | не длиннее 20 символов, цифры, пробелы, `+`, `-` |
| E-mail | нет | корректный адрес, уникален среди сотрудников |
| Кафедра, должность | да | существующие значения справочников |
| Учёная степень | да | `none`, `candidate`, `doctor`, `phd` |
| Дата приёма | да | корректная дата, не позже сегодняшней |
| Статус | да | `active`, `on_leave`, `dismissed` |
| Фото | нет | JPEG, PNG или WebP, не более 2 МБ |

Удаление сотрудника, по которому есть кадровые приказы, запрещено: Система сообщает,
что нужно изменить статус на «Уволен».

#### 4.2.3. Функция «Заявки на отпуск»
Правила (реализуются в классе `App\Services\LeaveRequestRules`):
1. Дата окончания не раньше даты начала.
2. Дата начала не раньше текущей даты.
3. Ежегодный отпуск (`annual`) — не более 56 календарных дней в одной заявке.
4. Допустимые переходы статусов:

| Текущий статус | Действие | Роль | Новый статус |
|---|---|---|---|
| pending | approve | head, admin | head_approved |
| pending | reject | head, admin | rejected |
| head_approved | approve | hr, admin | approved |
| head_approved | reject | hr, admin | rejected |
| approved, rejected | любое | любая | переход запрещён |

5. Заведующий принимает решения только по заявкам сотрудников своей кафедры и не может согласовать
   собственную заявку.
6. При утверждении (`approved`) Система в одной транзакции создаёт приказ типа `leave`
   с номером `ОТ-<год>-<номер заявки>`.

#### 4.2.4. Функция «Отчёт "штат по кафедрам"»
Таблица: факультет, кафедра, всего сотрудников (без уволенных), из них ППС, с учёной степенью,
в отпуске; итоговая строка. Отчёт можно распечатать (стиль для печати скрывает меню).

#### 4.2.5. Функция «Живой поиск»
При вводе в поле поиска (`#employee-search`) браузер через 300 мс после паузы запрашивает
`/api/employees?q=<строка>` и перерисовывает строки таблицы (`#employees-tbody`) без перезагрузки страницы.
Пустая строка возвращает весь список (не более 50 записей). Формат ответа — массив объектов:

```json
[
  {"id": 2, "full_name": "Рахимов Фарход Джамшедович",
   "department": "Кафедра программирования и информационных систем",
   "position": "Старший преподаватель", "phone": "+992 92 701 11 02",
   "hire_date": "2014-09-01", "status": "active"}
]
```

Сервер: 1 vCPU, 1–2 ГБ RAM, 20 ГБ SSD. Клиент: любой ПК или смартфон с современным браузером.

#### 4.3.7. Методическое обеспечение

## 7. Требования к подготовке объекта автоматизации к вводу системы в действие

1. Подготовить сервер (VDS) и доменное имя, настроить DNS-запись типа A.
2. Перенести справочники (факультеты, кафедры, должности) и карточки сотрудников из Excel
   (импорт через CSV или ручной ввод).
