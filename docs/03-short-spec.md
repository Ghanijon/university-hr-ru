# 3. Краткое техническое задание

Проект: **university-hr** — кадровая информационная система вуза. Версия документа: 1.0.

Краткое ТЗ занимает 1–2 страницы и отвечает на три вопроса: **что** делает система, **для кого**
и **что входит в первую версию** (MVP). Полное ТЗ по мотивам ГОСТ 34.602 будет составлено на день 8.

## 3.1. Назначение

Веб-приложение для отдела кадров вуза: единая база сотрудников, электронное согласование отпусков,
поиск и отчёты. Пользователи: администратор (`admin`), специалист отдела кадров (`hr`),
заведующий кафедрой (`head`), сотрудник (`employee`).

## 3.2. Функциональные требования

| Код | Требование |
|---|---|
| FR-01 | Вход по логину и паролю, выход из системы. Доступ к страницам — только после входа |
| FR-02 | Разграничение прав по четырём ролям (см. матрицу 3.6) |
| FR-03 | Список сотрудников с поиском по ФИО, фильтром по кафедре и статусу, пагинацией по 10 записей |
| FR-04 | Просмотр карточки сотрудника |
| FR-05 | Создание, редактирование и удаление сотрудника (роли `admin`, `hr`) |
| FR-06 | Загрузка фото сотрудника (JPEG/PNG/WebP, не более 2 МБ) |
| FR-07 | Справочник кафедр с факультетами и заведующими |
| FR-08 | Справочник должностей с категорией |
| FR-09 | Подача заявки на отпуск сотрудником |
| FR-10 | Согласование заявки заведующим кафедрой, утверждение отделом кадров, отклонение на любом этапе |
| FR-11 | Главная страница (dashboard): ключевые цифры и последние заявки |
| FR-12 | Отчёт «штат по кафедрам» |
| FR-13 | Кадровые приказы (приём, перевод, увольнение, отпуск) |
| FR-14 | Живой поиск сотрудников (JSON API `/api/employees?q=`) |
| FR-15 | Экспорт списка сотрудников в CSV |

## 3.3. Нефункциональные требования

| Код | Категория | Требование |
|---|---|---|
| NFR-01 | Безопасность | Пароли хранятся только как хеш (`password_hash`, bcrypt) |
| NFR-02 | Безопасность | Защита от SQL-инъекций (prepared statements), XSS (экранирование вывода), CSRF (токен в каждой POST-форме) |
| NFR-03 | Производительность | Любая страница открывается быстрее 1 с при 1000 сотрудников в базе |
| NFR-04 | Совместимость | Последние версии Chrome, Firefox, Edge; мобильные браузеры от 360 px ширины |
| NFR-05 | Локализация | Интерфейс на русском; хранение кириллицы без искажений — кодировка utf8mb4 |
| NFR-06 | Удобство | Любая типовая операция — не более 3 переходов от главной страницы |
| NFR-07 | Надёжность | Ежедневная резервная копия базы данных |
| NFR-08 | Сопровождение | Код в Git, понятная структура MVC, комментарии к ключевым местам |

## 3.4. Пользовательские истории (user stories)

Формат: «Как **<роль>**, я хочу **<действие>**, чтобы **<ценность>**». У каждой истории есть
критерии приёмки (acceptance criteria) и приоритет MoSCoW.

| ID | История | Критерии приёмки | MoSCoW |
|---|---|---|---|
| US-01 | Как **пользователь**, я хочу войти по логину и паролю, чтобы работать со своими данными | Неверный пароль → сообщение «Неверный логин или пароль»; после входа открывается главная | Must |
| US-02 | Как **специалист ОК**, я хочу видеть список сотрудников с поиском, чтобы быстро найти нужного | Поиск по части фамилии; фильтр по кафедре и статусу; по 10 записей на странице | Must |
| US-03 | Как **специалист ОК**, я хочу добавлять и редактировать сотрудника, чтобы данные были актуальны | Обязательные поля проверяются; e-mail уникален; после сохранения — сообщение об успехе | Must |
| US-04 | Как **специалист ОК**, я хочу загрузить фото сотрудника, чтобы карточка была наглядной | Принимаются JPEG/PNG/WebP до 2 МБ; файл другого типа отклоняется с сообщением | Must |
| US-05 | Как **сотрудник**, я хочу подать заявку на отпуск онлайн, чтобы не ходить по кабинетам | Даты обязательны; окончание не раньше начала; начало не в прошлом; статус «Ожидает» | Must |
| US-06 | Как **заведующий кафедрой**, я хочу согласовать или отклонить заявку своего сотрудника | Видны только заявки своей кафедры; кнопки доступны только для статуса «Ожидает» | Must |
| US-07 | Как **специалист ОК**, я хочу утвердить согласованную заявку, чтобы оформить отпуск | Кнопка «Утвердить» доступна только для статуса «Согласовано зав. кафедрой» | Must |
| US-08 | Как **администратор**, я хочу вести справочники кафедр и должностей | Список кафедр с факультетом и заведующим | Must |
| US-09 | Как **сотрудник**, я хочу видеть статус своих заявок | В списке только свои заявки, статус выделен цветом | Must |
| US-10 | Как **проректор**, я хочу отчёт «штат по кафедрам», чтобы планировать нагрузку | Таблица: кафедра, всего, со степенью, в отпуске; итоговая строка | Should |
| US-11 | Как **специалист ОК**, я хочу оформлять приказы, чтобы вести кадровый документооборот | Уникальный номер приказа; тип; привязка к сотруднику | Should |
| US-12 | Как **специалист ОК**, я хочу, чтобы таблица сотрудников обновлялась прямо при вводе фамилии (живой поиск) | Таблица обновляется через 300 мс после паузы ввода, без перезагрузки страницы | Should |
| US-13 | Как **специалист ОК**, я хочу выгрузить список в CSV, чтобы открыть его в Excel | Файл открывается в Excel с корректной кириллицей | Could |
| US-14 | Как **внешняя система**, я хочу получать данные сотрудников через REST API | JSON, только для авторизованного пользователя | Could |
| US-15 | Как **сотрудник**, я хочу получать уведомление по e-mail о решении по заявке | Письмо при смене статуса | Won't (в этой версии) |
| US-16 | Как **бухгалтер**, я хочу, чтобы система считала отпускные | — | Won't (в этой версии) |

## 3.5. Приоритизация MoSCoW и MVP

- **Must have** (обязательно, без этого система бесполезна): US-01 – US-09.
- **Should have** (важно, но можно отложить на неделю): US-10 – US-12.
- **Could have** (желательно, если останется время): US-13, US-14.
- **Won't have this time** (не в этой версии): US-15, US-16.

**MVP** (minimum viable product) = все истории Must: вход и роли, CRUD сотрудников, справочники,
заявка на отпуск с двухуровневым согласованием, список с поиском/фильтром/пагинацией, фото сотрудника.
В учебном проекте дополнительно реализуются US-10 (отчёт), US-12 (живой поиск) и US-14 (простой JSON API),
потому что на них удобно показывать темы курса.
